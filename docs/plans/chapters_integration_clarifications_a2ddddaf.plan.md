# Главы Matroska XML — зафиксированные решения и оставшиеся дефолты

## Что за формат в примере

Это **XML глав Matroska** (как выдаёт `mkvextract chapters` у `.mkv`):

- Корень `Chapters` → `EditionEntry` → несколько `ChapterAtom`.
- У каждой главы: `ChapterTimeStart`, блок `ChapterDisplay` с `ChapterString`, `ChapterLanguage`, опционально `ChapLanguageIETF`.

Текущий парсер в `[parseChaptersWithMkvExtract](c:\Users\icehole\git\DubbingTool\src\core\workflowmanager.cpp)` уже читает этот XML для поиска времени эндинга по имени главы. Сборка финального MKV **пока не прокидывает** главы (`--chapters` закомментирован ~строка 2014). Для MP4 ffprobe вызывается без `-show_chapters`.

### Поиск главы с эндингом (ТБ)

**Логику поиска главы по `endingChapterName` / `m_parsedEndingTime` не трогать**, если в ней нет подтверждённых багов. Новая функциональность переноса глав в контейнеры должна строиться **рядом** (отдельный путь данных: «список глав для mux»), без переписывания этого поиска ради «унификации».

## Решения заказчика (зафиксировано)

### 1. Наличие глав в результате

Если **есть** откуда взять главы (встроенные в исходник или выбранный пользователем XML), их нужно **перенести и в финальный MKV, и в финальный MP4**.

Если **нет** ни встроенных глав в MKV/MP4, ни файла от режиссёра (пользователь не указал) — **не считать это ошибкой** с точки зрения остановки пайплайна: не ломать сборку; в логе предупредить, что главы в выходе не попадут.

### 1a. «Этот релиз ждёт главы» (чтобы отличить забыли от нормы)

Нужно **закрепить в шаблоне/настройках релиза** явный признак, например **«для этого релиза ожидаются главы»** (булево поле).

- Если признак **включён**, а после выбора источника **глав так и нет** (ни в контейнере, ни внешний файл не дали / пусто) — показать **заметное предупреждение** (и по смыслу: возможно пользователь **забыл** приложить свой XML, как просили).
- Если признак **выключен** — отсутствие глав считать **нормальным** (режиссёр не прислал, релиз без глав), без «крикливого» предупреждения (достаточно нейтральной строки в логе при желании).

Точное имя поля и место в UI (редактор шаблона / мастер) — на этапе реализации.

### 2. Источник глав

Должна быть **возможность выбора**:

- **встроенные** главы из исходного контейнера (MKV через mkvextract; MP4 через ffprobe `-show_chapters` / метаданные), и
- **предоставленные пользователем** (внешний файл в формате Matroska chapter XML, как `12_chapters.xml`).

При конфликте приоритет нужно явно зашить в UI/логике (например «явно выбранный файл перекрывает встроенное»).

### 3. Переводы / несколько названий: MKV vs что описывает ffmpeg для MP4

**Matroska (исходный XML):** несколько `ChapterDisplay` с разными `ChapterLanguage` на один `ChapterAtom` — это **часть модели** контейнера (не предположение).

**Что говорит документация ffmpeg про перенос метаданных и глав в файлы:**

- Формат **ffmetadata** ([раздел Metadata в ffmpeg-formats](https://ffmpeg.org/ffmpeg-formats.html#Metadata-1)): секции `[CHAPTER]` с полями `START`/`END` (и опционально `TIMEBASE`); в **примере из документации** у каждой секции главы задаётся одна пара ключ/значение для названия — `title=chapter \#1`. Документ описывает «per-chapter metadata», но **не** описывает несколько альтернативных `title` с языковыми тегами на одну и ту же секцию `[CHAPTER]` как стандартный сценарий.
- **Muxer MOV/MP4** ([тот же документ, секция про QuickTime/MOV family](https://ffmpeg.org/ffmpeg-formats.html)): для записи в контейнер семейства MOV/MP4 упоминаются **Nero chapter markers (атом `chpl`)** и **QuickTime chapter track**; опция `disable_chpl` отключает запись Nero-глав. Это про **механизмы разметки по времени**, а не про документированную в этом месте **мультиязычность имён** глав.

**Вывод:** утверждение «в типичном пути ffmpeg в MP4 на одну метку времени получается **одна** строка названия» опирается на **описанный формат ffmetadata и отсутствие в этой главе документации схемы «несколько переводов на одну главу»**, а не на догадку о «запрете» в ISO. Отдельные расширенные схемы ISOBMFF для локализованных метаданных **в общем случае не заменяют** простой путь `map_metadata` + ffmetadata, который проект, скорее всего, будет использовать.

**Telegram:** поведение клиента по главам **не описано** в ffmpeg; проверка — только тестовым файлом на целевом клиенте.

**Для реализации:** при экспорте в MP4 задавать **одно** отображаемое имя на главу (например первый `ChapterString` из MKV-XML или выбранный язык позже), если не появится отдельное требование и подтверждённый способ mux.

### 4. Concat / сдвиги таймкодов

**Копировать главы без сложного пересчёта.** Допустимы сдвиги **порядка десятков миллисекунд** относительно идеала — **не критично**, не требуется отдельная политика «пересчитать от нуля» или «отключить при concat».

## Оставшиеся мелкие дефолты (можно не выносить на заказчика)

- **Несколько `EditionEntry`:** по умолчанию брать издание с `EditionFlagDefault==1`, иначе первое `EditionEntry`.
- **Вложенные `ChapterAtom`:** если не нужна иерархия в UI — обходить дерево в плоский список таймкодов в порядке `ChapterTimeStart`, либо только «листья» (уточнить при кодировании, если встретятся реальные файлы).
- **Сопоставление `endingChapterName` с XML:** не менять поведение без бага (см. выше).

## Технические опоры

- **MKV:** `mkvmerge --chapters <file.xml>` принимает тот же XML, что в примере; включить в цепочку сборки вместо закомментированного варианта с источником по выбору пользователя.
- **MP4:** ffmpeg/ffprobe — чтение глав из исходника; запись через типичный путь **ffmetadata** + `-map_metadata` / копирование потоков с метаданными; `+faststart` уже фигурирует в concat-пути — при желании проверить отображение глав в целевом плеере на реальном файле.
